# alloy-agent 설계

작성 2026-10-27. 상태: 채팅에서 승인됨, 문서 검토 대기.

## 목표

사용자가 원하는 강재 물성을 자연어로 말하거나 스펙 시트를 올리면, Muse Spark 에이전트가 이를
제약조건으로 바꾸고, 불확실성을 아는 예측기로 조성을 탐색하고, 트레이드오프를 보여준 뒤, 보정된
±2σ 구간과 근거가 붙은 후보 순위를 돌려준다. 학습 범위 밖 후보는 숨기지 않고 표시한다. 답에 나오는
숫자는 전부 툴 출력에서 온다.

겨냥하는 심사 가중치: Impact 30, Meta 툴링 25, Demo 25, Technical depth 20.
보너스: Best Agentic Use-Case, Best Open Weight(Baseten의 Muse Spark Open).

## 제약

- 2026-10-27 ~ 11-04, 혼자 개발. 기능 동결 11/2(KST). 10/31과 11/1은 거의 작업 불가.
- 데이터: Figshare Steel Strength(MIT). 강재 312건, 원소 13종 → YS(312행), UTS·El(303행).
  대부분 마레이징/초고강도강. DATA.md 참고.
- 대회 이전 코드·모델·데이터는 쓰지 않는다(MAPS 미사용).
- 제품은 전부 영어(UI, 프롬프트, 툴 스펙, 에러, README). 에이전트는 사용자 언어로 답한다.
  이 설계 문서는 내부용이라 한국어로 쓴다.

## 아키텍처

LLM 에이전트 하나, 툴 3개, 결정적인 코드 검증기. 비판 역할은 두 번째 LLM이 아니라 코드가 맡는다.

```
Gradio UI ── 채팅 + 스펙 업로드 | 트레이스 패널 | Pareto 산점도 | 후보 표(±2σ 막대)
   │ gr.State {last_front, candidates, trace}
   ▼
intake.py   (선택) PDF/이미지 → muse-spark-1.3 → Constraints JSON (pydantic)
agent.py    루프: LLM ⇄ 툴, 상한, 최종 답 조립, 검증기 재시도
tools.py    predict · search · pareto (pydantic 인자 검증, 에러는 툴 결과로 반환)
predictor.py OpenPredictor: 타깃별 부트스트랩 앙상블 + 스칼라 k 보정 + kNN 범위 검사
verify.py   본문 숫자 ⊆ 툴 출력 ∪ 사용자 숫자 (1% 허용오차), OOD 후보는 반드시 표시
data.py     다운로드 + 체크섬 (완료)
eval/       질의, run_eval.py → CSV, rediscovery.py (LLM 없음)
```

LLM 백엔드는 환경변수(`LLM_BASE_URL`, `LLM_MODEL`, 키)로 고른다. 에이전트 루프의 기본값은
Baseten `meta-models/muse-spark-open-1026`이고, 대안은 Meta `muse-spark-1.3`이다. 둘 다
OpenAI 호환이고 function tool이 동작한다(2026-10-27 확인).

## 구성요소

### predictor.py — OpenPredictor
- 입력: 원소 13종의 wt%. Fe는 나머지(balance)라서 들어와도 무시한다. 빠진 원소는 학습 데이터 중앙값으로 채운다.
- 타깃: YS, UTS, El을 각각 따로 학습한다. 해당 타깃 값이 있는 행만 쓴다.
- 모델: 타깃마다 sklearn 회귀기 하나를 부트스트랩으로 최대 20개 학습한다. 회귀기는 gradient
  boosting과 random forest 중 5-fold MAE가 더 좋은 쪽을 쓴다. μ는 앙상블 평균, σ_raw는 앙상블 표준편차다.
- 보정: 타깃마다 스칼라 k 하나를 정한다. 5-fold out-of-fold 행의 약 95%가 μ ± 2kσ_raw 안에
  들어오도록 고른다. 실제 포함률과 MAE는 README에 적는다.
- 범위 검사: 원소가 학습 min/max를 벗어나면 범위 밖이다. 추가로 표준화한 입력으로 학습 세트까지의
  kNN 거리(k=5)를 구하고, 학습 데이터끼리의 거리 95백분위수보다 멀면 표시한다.
- 인터페이스: `predict(comps: list[dict]) -> list[Prediction]`. search에서 쓰려고 배치로 받는다.
  Prediction에는 `{target: (mu, sigma)}`, `ood: bool`, `ood_reasons: list[str]`이 들어간다.

### tools.py — LLM에 노출하는 툴 3개
1. `predict(composition)`
   - 반환: YS·UTS·El의 μ와 보정된 σ, OOD 표시와 이유.
   - 모르는 원소 키는 검증 에러로 모델에 돌려준다.
2. `search(constraints, bounds?, n?)`
   - 후보 생성: 학습 행을 섭동하거나 서로 보간한다. 원소별 학습 min/max로 자르고, 사용자가
     준 범위가 있으면 그것도 적용한다.
   - 점수: 후보를 배치로 예측한 뒤, 제약마다 정규화한 여유를 구하고 그중 최솟값을 점수로 쓴다.
     - 최소 목표: (μ − 2σ − 목표) / 범위
     - 최대 목표: (목표 − (μ + 2σ)) / 범위
     - 범위 = 그 타깃의 학습 데이터 최댓값 − 최솟값.
     - 점수 ≥ 0이면 feasible이다.
   - 반환: 상위 n개 후보(기본 5개)와 각 후보의 예측값, 점수, OOD 표시.
   - feasible한 후보가 없으면 `binding`도 돌려준다. 가장 나은 후보에서 어떤 제약이 얼마나
     모자라는지다. 에이전트는 이걸 보고 제약을 완화하거나 범위를 좁힌다.
3. `pareto(objectives, constraints?, bounds?)`
   - search와 같은 후보 풀을 쓴다. 주어진 목표(예: YS 최대, El 최대)에 대해 μ 기준으로 지배되지 않는 후보만 남긴다.
   - `rank = margin / σ` 열을 붙인다. 유망하면서 불확실성이 큰 후보를 "다음 실험"으로 추천하는 데 쓴다.
   - 전선은 세션 상태에 저장한다.

툴 인자는 모두 pydantic으로 검증한다. 검증 에러와 실행 에러는 `{"error": "..."}` 형태의 툴 결과로 돌려준다.

### agent.py — 루프
- 시스템 프롬프트:
  - 툴 사용 규칙.
  - 데이터 범위(마레이징/초고강도강, 학습 범위).
  - "툴이 돌려주지 않은 숫자는 절대 말하지 말 것."
  - 사용자 언어로 답할 것.
- 사용자 턴마다:
  - 툴 호출 최대 6회, 재탐색 루프 최대 2회(search → binding → 조정한 search).
  - 턴별 토큰 상한과 세션 전체 상한을 둔다.
  - 추론 토큰이 `max_tokens`에서 차감되므로 `max_tokens`는 1000 이상으로 둔다.
- 최종 답:
  - 후보 표는 코드가 마지막 search/pareto 출력으로 채운다.
  - LLM은 설명 문장만 쓴다(근거, 트레이드오프, 다음 실험).
- 검증 단계: 실패하면 검증기 메시지를 user 역할 메모로 한 번 돌려주고 모델이 다시 쓰게 한다.
  또 실패하면 검증되지 않은 숫자를 본문에서 지우고 코드가 채운 표만 남긴다. 루프를 반복하지 않는다.
- 멀티턴: 직전 전선과 후보를 요약해서 컨텍스트에 넣는다. "more elongation" 같은 후속 요청이
  오면 에이전트가 제약을 바꿔 pareto/search를 다시 호출한다. 재탐색 전용 코드는 따로 만들지 않는다.
- 매 턴의 메시지, 툴 호출, 소요 시간, 토큰 사용량을 `runs.jsonl`에 추가한다.

### verify.py
- 본문에서 숫자를 뽑는다.
- 각 숫자는 상대 오차 1% 안에서 다음 중 하나와 맞아야 한다:
  - 그 턴의 툴 출력에 있는 값
  - 사용자 메시지에 있는 숫자
  - 작은 허용 목록(예: "2σ"의 2, "95%"의 95)
- 본문이 추천하는 후보가 OOD라면, 표나 본문에 OOD 표시가 있어야 한다.
- 결과는 `ok` 또는 문제 목록이다.

### intake.py — 스펙 시트 업로드(멀티모달)
- 업로드한 PDF나 이미지로 `muse-spark-1.3`을 한 번 호출한다.
- 모델은 `Constraints` pydantic 모델에 맞는 JSON을 돌려줘야 한다. 목표값의 최소/최대와 선택적인 원소 상한이 들어간다.
- 파싱에 실패하면 에러를 보여주고, 사용자가 제약을 직접 입력하게 한다.
- 데모용 고정 파일 2개로만 테스트한다.

### app.py — Gradio
- 왼쪽: 채팅과 스펙 시트 업로드 버튼.
- 오른쪽:
  - 트레이스 패널(툴 → 인자 → 결과 요약 → 검증 상태). Markdown/JSON으로 표시한다.
  - Pareto 산점도(`gr.ScatterPlot`).
  - ±2σ 막대가 붙은 후보 표.

## 평가
- `eval/queries.jsonl`: 영어 목표 질의 20개. feasible, infeasible, 트레이드오프, OOD를 유도하는 질의, 후속 질의를 섞는다.
- `eval/run_eval.py`:
  - 질의마다 백엔드별로 한 번씩 실행하고, 툴 출력은 캐시한다.
  - CSV에 기록하는 항목:
    - 성공 여부: 검증을 통과한 feasible 후보가 1개 이상이거나, infeasible 이유를 맞게 설명했는지.
    - 툴 호출 수, 지연 시간, 토큰 수.
    - OOD 비율, 검증 실패 수.
  - 두 백엔드를 비교하는 차트 1개를 함께 출력한다.
- `eval/rediscovery.py`:
  - LLM 없이 돌린다.
  - YS 상위 10% 강재를 빼고 다시 학습한 뒤, 그 강재들의 YS/El을 목표로 `search`를 돌린다.
  - 후보가 빼둔 강재의 최근접 이웃 거리 안에 들어오는지 확인한다.
  - 0건이 나와도 그대로 보고한다.

## 에러 처리
- 잘못된 툴 인자나 모르는 원소: 에러를 툴 결과로 돌려주고 모델이 다시 시도한다.
- LLM HTTP 에러나 타임아웃: 백오프를 두고 한 번 재시도한 뒤, UI에 에러를 보여준다. 데모용으로
  저장된 `runs.jsonl` 턴을 다시 보여주는 재생 모드를 둔다.
- 상한에 도달하면 에이전트는 가진 것으로 답해야 한다. 트레이스에 "cap reached"를 표시한다.

## 범위 밖
- 응력-변형률 곡선. 총 연신율만으로는 Hollomon 근사를 할 수 없다.
- 두 번째 LLM 비평자.
- 파인튜닝.
- MAPS 연동. 해커톤 이후 별도 브랜치에서 한다.
- Modal 배포. 시간이 남을 때만 한다.

## 남은 위험
- 데이터가 작아서 σ가 크다. 발표 메시지는 "자기가 모르는 걸 아는 에이전트"이고, 정확도는 백엔드를 바꾸면 따라온다.
- 추론 모델이라 라이브 데모에서 지연이 생길 수 있다. Baseten을 기본값으로 쓰고, 상한을 두고, 녹화본을 대비책으로 쓴다.
